把本次会话的有效产出(结论、理由、现状、下一步)蒸馏进「大脑仓库」,
让另一台机器的 agent 只读笔记就能接上思路。笔记一律用中文。

大脑仓库 = 集中存放所有项目笔记的私有 git 仓库,每台机器 clone 路径可以不同;
本 skill 不写死盘符,靠第 0 步自动定位。

### 第 0 步:定位大脑仓库(每台机器只需定位一次)

按顺序执行,取第一个命中:

1. 若 `%USERPROFILE%\.agent-brain` 文件存在 → 读其内容、去首尾空白,作为 `<大脑根>`。
2. 否则依次探测候选路径,第一个"存在且含 README.md"的即 `<大脑根>`:
   `G:\ai\agent-brain`、`D:\ai\agent-brain`、`E:\ai\agent-brain`、`%USERPROFILE%\agent-brain`。
3. 全部未命中 → 问用户:"大脑仓库 clone 在本机哪个路径?"回答即 `<大脑根>`。
4. 把 `<大脑根>`(一行、无引号)写入 `%USERPROFILE%\.agent-brain`;本机以后不再询问。
5. 校验 `<大脑根>` 下有 `.git`;没有 → 停止,提示用户先 clone 大脑仓库
   (步骤见 `<大脑根>\README.md` 的「新机器初始化清单」或 GitHub 仓库地址)。

### 第 1 步:准备信息

1. 项目名 = 当前工作目录的文件夹名。
2. 日期 = `Get-Date -Format yyyy-MM-dd`,时间 = `HH:mm`(pwsh)。
3. 机器代号:读 `<大脑根>\machines.md`,用 `$env:COMPUTERNAME` 查表;
   查不到 → 问用户"这台机器叫什么代号(如 B机)?",把
   `| COMPUTERNAME | 代号 | 角色 | 今日日期 |` 追加进表格(随大脑仓库一起提交)。
   角色可留空让用户补充。
4. 若 `<大脑根>\<项目名>\` 不存在 → 新建四件套:CONTEXT.md(最小骨架:
   项目是什么 / 当前阶段 / 关键文档 / 约定)、DECISIONS.md(空表头 + 一句使用说明)、
   NEXT.md(三区:进行中 / 下一步 / 已知坑)、JOURNAL\ 空目录。

### 第 2 步:采集项目代码状态(当前目录是 git 仓库时)

用 pwsh 采集并记下,供日志与提交使用:

- 分支:`git rev-parse --abbrev-ref HEAD`
- 短哈希:`git rev-parse --short HEAD`
- 未提交修改:`git status --porcelain`(非空 = dirty,列出文件)
- 远程:`git remote get-url origin`(失败 = 无远程)

当前目录不是 git 仓库 → 跳过本步,日志注明"项目尚无 git 仓库"。

### 第 3 步:写 JOURNAL

文件:`<大脑根>\<项目名>\JOURNAL\<日期>-<机器代号>.md`。
若已存在(同日同机再次收尾)→ 在文末追加 `## 第二次收尾 <时间>` 小节,**不覆盖**。

首次创建的骨架(按实际填写,宁短勿假):

```markdown
# <日期> — <机器代号>

## 本次做了什么
- (结论式 3~8 条:做了什么、为什么)

## 关键结论 / 决策摘要
- (详细决策在 DECISIONS.md,这里一句话带过;项目代码分支/commit: <分支> <短哈希>)

## 遗留 / 交给下一台机器
- (未完成事项、注意事项、复现命令)
```

### 第 4 步:更新 NEXT.md

重写 `<大脑根>\<项目名>\NEXT.md` 的三个区:

- **进行中**:当前半成品状态;没有写"无"。
- **下一步**:编号列表,每条是可直接开工的粒度。
- **已知坑**:踩过的坑与注意事项;没有写"暂无"。

规则:NEXT 只保留"当前断点"。本次已解决的旧条目**挪进第 3 步的 JOURNAL**,不许直接删除信息。
文末「最近更新」改为 `<日期> <机器代号>`。

### 第 5 步:追加 DECISIONS.md(可选)

本次会话若有**拍板**的方案/技术决策,在 `<大脑根>\<项目名>\DECISIONS.md` 追加:

```markdown
## <日期> <决策标题>

- **决定**:…
- **理由**:…
- **否决**:…(没有就省略本行)
```

没有拍板决策 → 整步跳过。"讨论中 / 待确认"的内容只进 JOURNAL,不进 DECISIONS。

### 第 6 步:提交与推送(顺序:先项目仓库,后大脑仓库)

**项目仓库**(仅当第 2 步采集到 dirty):

1. 列出未提交文件,问用户:"这些改动要一并提交吗?"
2. 同意 → `git add -A` + `git commit -m "wip: <日期> 收尾前提交"`;有远程则 `git push`。
3. 拒绝 → 不动项目仓库,直接进入大脑仓库步骤,并在汇报中提醒"项目代码未提交"。

push 被拒 → 先 `git pull --rebase` 再试一次;仍失败 → 报告用户,**不要强推**。

**大脑仓库**(总是执行):

```text
git -C "<大脑根>" add -A
git -C "<大脑根>" commit -m "handoff: <项目名> <日期> <机器代号>"
git -C "<大脑根>" push
```

push 被拒 → `git pull --rebase` 后重试一次;仍失败 → 报告用户;无远程 → 本地提交即可并告知。

### 第 7 步:汇报

向用户简要汇报:

- 写了 / 改了哪些 brain 文件;
- 两个仓库各自的提交与推送结果(含短哈希);
- 一句交接提示:"另一台机器 pull 后,对 agent 说『先读大脑仓库里 <项目名> 的笔记再继续』"。

### 红线(任何情况下不得违反)

1. 密钥、token、密码、内网地址、`.env` 内容**绝不**写入任何笔记文件;
   用户消息里出现敏感值时,笔记只写"涉及密钥配置(已脱敏)"。
2. 笔记只写结论和理由:**不搬运原始对话**,不贴大段代码(单段 ≤ 5 行)。
3. 不删除历史内容,只追加或按第 4 步规则挪动。
4. 假设接力模式,不处理合并:遇冲突按第 6 步规则,rebase 解决不了就停下来问用户。
